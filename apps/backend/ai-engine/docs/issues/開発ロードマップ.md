# 【親 issue】開発ロードマップ — gRPC 分離から ブロック UI まで

学習パイプライン単体（cold start / resume / checkpoint / validation / GPU）は
`feature/gpu-support` までで動作する。ここから先、`CLAUDE.md` の最終成果物
「ブロック UI で深層学習モデルを GUI 操作する」に向けた開発順序をまとめる。

個別 issue はそれぞれ独立ドキュメントにある。本 issue は**順序と依存関係の地図**。

---

## 全体像

```
[GUI/React]  ブロック UI ── model config を生成 ──┐
                                                   ▼
[Rust: training-api]  config 検証・ポリシー ── gRPC ──┐
                                                       ▼
[C++: ai-engine]  ModelFactory / 学習 / 推論 / capability  ← libtorch
```

- 交換フォーマット（model config = proto メッセージ）を軸に、上流（UI）と
  下流（C++ エンジン）を疎結合にする。
- **下流から先に作る**。UI は最後。手書き config で縦切りを通してから
  「config を吐く UI」を足す。

## Phase 2: gRPC 足回り（詳細は `grpc-layer.md`）

**ゴール**: 空の gRPC サーバーが起動し、`GetCapabilities` が Rust から叩ける。

- `apps/backend/proto/capabilities.proto`（`package aiengine.v1`）
- C++: `src/api/grpc/`（inbound adapter）、`ICapabilityProvider`（application ポート）、
  `CudaCapabilityProvider`（infrastructure）
- Rust: `apps/backend/training-api` crate（tonic + prost、クリーンアーキテクチャ）
- devcontainer を 2 サービス化（`ai-engine-dev` + `training-api-dev`）
- Dockerfile に gRPC / protobuf 追加、CMake で proto 生成

**この Phase の意味**: 機能ではなく「Rust ↔ C++ を gRPC でつなぐ配線」を最小コストで
確立する。以降の Phase はこの上に RPC を足すだけになる。

---

## Phase 3: config 方式 + 学習 RPC（詳細は `model-config-and-training-rpc.md`）

**ゴール**: 手書き config を Rust から投げ、C++ で学習が完走し checkpoint が出る。
GUI は不要（進捗はログ出力）。

主要な設計判断（この Phase で確定させる）:

1. **model config のグラフ表現** — 汎用ノード＋エッジ（`Node{id,type,params}` + `Edge`）。
   初期は `string model_config_json` で走らせ、固まってから構造化 message に。
2. **実行制御の方式** — 非同期 job 方式（`job_id` 発行 → 購読 → 停止）を推奨。
3. **レジストリ** — C++ に「type 文字列 → レイヤ / optimizer / loss 生成」の factory。
   `TorchModelFactory` を config グラフから組み立てるよう拡張。
4. **`ProgressUpdate` のフィールド** — GUI で見せたい要素（epoch / loss / metrics /
   phase / eta / checkpoint path）を先に予約。

成果物:

- `apps/backend/proto/training.proto`
- C++: レジストリ + `TorchModelFactory` 拡張 + `TrainingServiceImpl`
- Rust: 学習 RPC クライアント + config ローダ
- `configs/` にサンプル config（`conv_relu_smoke.json` 等）
- 2 コンテナ compose での疎通確認

---

## Phase 4: 推論 RPC（詳細は `inference.md`）

**ゴール**: 学習済み checkpoint を指定し、入力画像を推論して予測マスクを返す。
「構造をいじる → 学習 → 結果を目で見る」ループを閉じる。

- 学習と同じエンジンの「別の入口」。`IModel::forward` の分離（`validation.md` と共通）
- `inference.proto`（`Predict` RPC、当面 unary）
- streaming・ハードウェア I/O・無人稼働（ローカルセンサ用途）は段階 2 に分離

---

## Phase 5: React ブロック UI

**ゴール**: ブロックでモデル構造・optimizer・loss・活性化・パラメータを組み、
Phase 3 の model config を出力してバックエンドに投げる。

- `GetCapabilities`（or 拡張 RPC）が返す「type → params スキーマ」でパレットを駆動
- UI の状態が model config の Source of Truth。UI → config の一方向変換
- 学習の進捗（`StreamProgress`）をグラフ表示、推論結果（Phase 4）を画像表示
- フロント ↔ Rust は別 API（gRPC-web or REST。要検討）

---

## 進め方の原則

- **下流優先・縦切り**: 各 Phase で「Rust から叩けて C++ で完走する」ところまで通す。
  部分実装を横に広げない。
- **生成コードは境界に閉じる**: protobuf / tonic 型は C++ の adapter・infrastructure、
  Rust の adapters・infrastructure まで。ドメイン層は触らない。
- **依存方向**: `entities → application → adapters → infrastructure` を C++ / Rust 両方で維持。
- **ビルド**: C++ は `-j2` 制約。gRPC 導入でビルドが重くなるため、gRPC を別ターゲットに
  分けるか早めに判断（`grpc-layer.md` 参照）。
- **proto バージョニング**: `package ...v1`。`v1` 凍結前は自由に変更してよい。
  凍結後の破壊的変更は `v2`。
