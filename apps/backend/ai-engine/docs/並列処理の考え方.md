# 並列処理の考え方 — データ読み込みの並列化(`parallelFor` とスレッドプール)

学習中に GPU が待たされていた原因(データ読み込みの遅さ)を、バッチ内のサンプルを並列に読み込むことで解消した。その実装の背景にある考え方を、自分で実装し直せるように、順序立ててまとめる。

## 1. 背景

- 計測(`enable_time_measurement`)の結果、学習ループは、1バッチのデータが用意されるのを待つ時間が長かった。
- 1サンプルの読み込み(JPEG / PNG のデコード、色 → クラス ID の変換、リサイズ、正規化)に約 36 ms かかり、GPU の計算(約 10 ms / サンプル)の約 3 倍だった。
- 読み込み側の単純な無駄(画素ごとのヒープ確保など)を直したあとも、なお 3 倍近い差が残っていたため、並列化した。

## 2. 用語

| 用語 | 意味 |
|---|---|
| 並列(parallel) | 複数の処理が、同時に(複数のコアで)実行されること |
| 並行(concurrent) | 複数の処理が、互いに独立に進行しているように見えること(1コアの切り替えでも成り立つ) |
| 自明に並列化できる(embarrassingly parallel) | 仕事を、互いに依存しない小さな仕事に分けられる問題。今回のバッチ内のサンプルが、これに当たる |
| データ競合(data race) | 複数のスレッドが、同じメモリを、同期なしで読み書きし、少なくとも1つが書き込みである状態。C++ では未定義動作 |
| アトミック操作(atomic) | 他のスレッドから見て、途中の状態が観測されない、不可分な操作。`std::atomic` |
| ミューテックス(mutex) | 同時に1つのスレッドだけが、保護された範囲に入れるようにする道具 |
| 条件変数(condition variable) | ある条件が成り立つまで、スレッドを眠らせ、成り立ったときに、起こす道具 |
| RAII | 資源の確保を、オブジェクトの生成に、解放を、破棄に結びつける手法(`lock_guard`、スレッドの `join` など) |

## 3. どこを並列化するか

### 出発点

- 並列化する対象: **1サンプルの読み込みと前処理**(`for` ループの中身のすべて)。1バッチ内の 16 / 32 個のサンプルは、互いに依存しない。
- 守る条件: バッチ内のサンプルの**並び**は、逐次のときと同じにする。既存の設計(`PreFetch`、`IDatasetRepository`)は、壊さない。
- 場所: サンプルを添字で取り出せる `SegmentationDatasetRepository::getNextBatch()`。`PreFetchDatasetRepository` は、状態を持つ内側を逐次に呼ぶ設計なので、その位置では並列にできない。

### 2つの方式

```
【案A(実装した方式)】1バッチの中を、分担する
  バッチ k : スレッド1 → サンプル 1, 5, 9,  13
             スレッド2 → サンプル 2, 6, 10, 14      16 サンプルを、4 スレッドで、同時に処理
             スレッド3 → サンプル 3, 7, 11, 15
             スレッド4 → サンプル 4, 8, 12, 16
             (全部終わったら、バッチ k が完成)→ 次に、バッチ k+1 へ

【案B(採用しなかった方式)】ワーカーごとに、1バッチ丸ごと担当する
  ワーカー1 → バッチ k   の 16 サンプルを、順番に処理
  ワーカー2 → バッチ k+1 の 16 サンプルを、順番に処理    複数のバッチを、同時に作る
```

| | 案A(実装) | 案B(未実装) |
|---|---|---|
| 同時に作るバッチの数 | 1つ(`PreFetch` が先読みするのも、次の1バッチだけ) | ワーカーの数だけ |
| `batch_size=1` のとき | 効果なし(並列にできるサンプルが1つ) | 効果あり |
| メモリ | 1バッチ分 | ワーカー数 × 1バッチ分 |
| 順序の管理 | 添字の位置に書くだけ | 順序付きのキューが必要 |
| 設計の変更 | 小さい(`getNextBatch()` の中だけ) | 大きい(バッチを、添字で作れる形にする必要がある) |

学習データは 2000 枚以上、バッチサイズは 16 または 32 の予定で、案Aで、必要な並列度(約 4)を、まかなえるため、案Aにした。

### なぜ、バッチごと(案B)にしなかったか

理由は、次の5点。

1. **既存の設計に、収まる。** 案Aの変更は、`getNextBatch()` の `for` ループ1つと、`IParallelExecutor` の注入だけ。案Bは、バッチを「何番目」と指定して作れる形(状態を持たない `getBatch(k)`)に変える必要がある。現在の `IDatasetRepository`(`hasNext` / `getNextBatch` / `reset`)は、状態を持つ逐次の契約なので、契約の見直しか、新しいポートが要る。あわせて、エポックの境目(`reset()`)と、先読み(`PreFetch`)との、整合も取り直しになる。
2. **必要な並列度を、まかなえる。** バッチ内に 16〜32 個のサンプルがあり、必要なスレッドは約 4 本。実測でも、4 スレッドで、GPU の計算時間に追いついた。
3. **メモリが少ない。** 同時に作るバッチは1つ。案Bは、ワーカー数 × 1バッチ分になる(コンテナは約 7GB)。
4. **順序と検証が、単純。** 結果を、添字の位置に書くだけで、並びは保たれる。案Bは、完成順がばらつくバッチを、順番に並べ直す仕組み(順序付きのキュー)が、必要で、検証も、複雑になる。
5. **後から、案Bへ進める。** `IParallelExecutor` は、そのまま使える(仕事の単位を、「サンプル」から「バッチ」に変えるだけ)。案Aを入れることは、案Bを、閉ざさない。

案Aの弱点(トレードオフ)

- **バッチごとに、同期の壁がある。** 1バッチは、最も遅いサンプルが終わるまで完成しない。動的な割り当てで、偏りは減らせるが、バッチの終わりに、遊ぶスレッドが、少し出る(4 スレッドで、理想の 551 / 4 ≒ 138 ms に対し、実測は 165 ms)。
- **`batch_size` が小さいと、効果が出ない。** 並列にできるサンプルが、バッチ内の数しかない。
- **先読みは、次の1バッチだけ。** 準備の時間が、ばらつくと、GPU が待つ可能性がある。

案Bが向くのは、バッチサイズが小さい(1〜4 程度)とき、バッチサイズより多くのスレッドを、使いたいとき、バッチごとの同期の壁を、なくしたいとき。

## 4. 設計の考え方

### ① 契約(インターフェース)から書く

「`count` 個の独立な仕事を、並列に実行して、全部終わるまで待つ」だけを、`parallelFor(count, body)` として決める([IParallelExecutor.hpp](../src/training/application/interfaces/IParallelExecutor.hpp))。契約には、次の点を書いた。

- `body(i)` は、各 `i` について、ちょうど1回ずつ呼ばれる(順序とスレッドは不定)。
- 戻った時点で、すべての `body` が、終わっている(だから、`body` は、ローカル変数を、参照でキャプチャしてよい)。
- 例外が起きても、残りは実行し、最初の例外を、呼び出し元に、再送出する。

契約を先に書くと、実装の正しさを、テストで確かめられる。

### ② 逐次版を先に作る

`SequentialExecutor` は、遅くても、確実に正しい版で、並列版の**基準(正解)**になる。並列版が、逐次版と、同じ結果を返すかを比べる、という検証の形は、並列処理のテストの基本。

### ③ 依存性の注入(DI)

読み込みのクラス(`SegmentationDatasetRepository`)は、スレッドを知らずに、`IParallelExecutor` の `parallelFor` を呼ぶだけ。使う実装は、合成層(`TrainingApp.cpp`)が、`.config` の `num_workers` で選ぶ。

| `num_workers` | 使う実装 |
|---|---|
| 1(既定) | `SequentialExecutor`(並列化前と、同じ動作) |
| 2 以上 | `ThreadPoolExecutor(num_workers)`(学習用・検証用で、1つを共有する) |

## 5. 核になる4つの考え方

### (a) データ競合を、ロックで防ぐ前に、設計でなくす

`vector::push_back` を、複数のスレッドから、呼ぶと壊れる。ロックで守ると、待ちが発生して、並列の意味が薄れる。代わりに、**各仕事が、自分専用の場所にだけ書く**ように設計する。

```cpp
std::vector<X> results(count);                                   // 先に、必要な数だけ確保する
parallelFor(count, [&](size_t i) { results[i] = compute(i); });  // i 番目は、i 番目にだけ書く
```

書き込み先が重ならないので、ロックは不要で、結果の並びは、実行の順序と無関係に、添字の順になる。

`ImageData` は既定コンストラクタを持たないため、結果の領域は `std::vector<std::optional<ImageData>>` で、先に確保した。

### (b) 仕事の配り方: 共有カウンタで、早い者勝ち(動的な割り当て)

最初に、「スレッド0は 0〜3、スレッド1は 4〜7…」と固定で割り振ると、仕事ごとの時間がばらつくとき(ファイルサイズなど)、早く終わったスレッドが遊んでしまう。共有の「次に取る添字」を1つ持ち、空いたスレッドが、順に取る。

```cpp
std::atomic<size_t> next{0};
// 各スレッド:
while (true) {
    size_t i = next.fetch_add(1);      // 不可分に、1 増やして、増やす前の値を得る
    if (i >= count) break;
    body(i);
}
```

`fetch_add` は、複数のスレッドが、同時に呼んでも、同じ値を、2人が、受け取ることがない、と CPU が保証する命令。

### (c) 完了の同期: 全部終わるまで待つ

添字を取り終えても、他のスレッドが、最後の仕事を、実行中かもしれない。「終わった仕事の数」を数え、`count` に達するまで、呼び出し元を待たせる。待つには、条件変数を使う。

```cpp
std::unique_lock lock(m);
cv.wait(lock, [&]{ return finished == count; });   // 条件を、述語(ラムダ)で渡す
```

述語つきの `wait` は、疑似的な起床(通知がないのに、目が覚めること)にも、対応できる。必ず述語を渡す。

### (d) 呼び出したスレッドも、仕事に加わる

呼び出し元が、ただ待つだけだと、そのスレッドが無駄になる。呼び出し元も、仕事を取れば、`num_workers` を N にしたとき、専用のスレッドは N−1 本で済む。N=1 のときは、専用のスレッドが 0 本で、逐次実行と、同じになる(既定値が、安全な理由)。

## 6. 自分で実装するときの、段階の踏み方

1つずつ、動くことを確かめながら進めると、バグの原因を、切り分けられる。

| 段階 | 作るもの | 学ぶこと | 確認の方法 |
|---|---|---|---|
| 1 | `IParallelExecutor` と `SequentialExecutor` | 契約の書き方 | 各添字が、1回ずつ呼ばれるテスト |
| 2 | 素朴な並列版: 呼び出しのたびに、`std::thread` を N 本作って、`join` する | `std::thread`、`join`、データ競合が、なぜ起きるか | 段階1と結果が一致するか。速くならなくてよい |
| 3 | 共有の `atomic` カウンタで、仕事を配る | `fetch_add`、動的な割り当て | 同上。仕事の時間が、ばらつくデータで、偏りが減るか |
| 4 | プール: スレッドを、コンストラクタで1回だけ作り、使い回す(条件変数で待機) | 条件変数、述語、デストラクタでの停止と `join`(RAII) | 100回繰り返しても壊れないか |
| 5 | 例外の伝搬(`std::exception_ptr`) | 別スレッドの例外は、捕まえないと、`std::terminate` で止まる | body が例外を投げるテスト |
| 6 | 複数の呼び出し元が、同時に使える | `shared_ptr` による状態(Job)の共有と寿命 | 3つのスレッドから同時に呼ぶテスト |

段階2の、スレッドを毎回作る方式は、遅い(スレッドの生成は、数十〜数百マイクロ秒かかる)ので、段階4の、プールにする**動機**が、実感できる。

## 7. つまずきやすい点

- **通知の取りこぼし(lost wakeup)**: 待つ側が、条件を確認してから、待ち始めるまでの間に、通知が先に来ると、永遠に起きない。「同じミューテックスを取ってから、通知する」「待つ側は、そのミューテックスの下で、条件を確認する」というルールで、防ぐ。
- **仕事の状態の寿命**: プールのスレッドが `Job` を持ったまま、呼び出し元の `parallelFor` が戻ると、参照がぶら下がる。`shared_ptr` で共有し、`body` へのアクセスは、**添字を取れたときだけ**(その時点では、呼び出し元は、まだ戻っていない)という不変条件で守る。
- **デストラクタでの停止**: 停止の合図を出して、全スレッドを `join` しないと、破棄されたメンバに、スレッドがアクセスする。
- **例外**: 別スレッドで、例外が投げられ、捕まえないと、プログラムが強制終了する。`std::exception_ptr` で、呼び出し元に運ぶ。
- **同じ `output_dir` を使った、連続の実験**: 学習の再開機能(`model_last.pt` からの自動再開)のため、2回目の実行が、学習せずに終わることがある。計測のときは、実行ごとに、出力先を分ける。

## 8. 検証の考え方(4本立て)

1. **基準との比較**: 逐次版と、結果が一致するか(単体テスト、実データ)。
2. **繰り返し**: まれにしか起きないバグを、100回程度の実行で、あぶり出す。
3. **ThreadSanitizer**(`-fsanitize=thread`): データ競合を、機械的に検出する。この環境では、`setarch "$(uname -m)" -R ./実行ファイル` で、アドレスのランダム化を切らないと、起動しない。
4. **計測**: 本当に速くなったか(`num_workers` を変えて)。速くならないなら、別の所に、ボトルネックがある。

### この実装での結果

- 単体テスト([parallel_executor_test.cpp](../tests/parallel_executor_test.cpp))58 項目が通った。全テスト実行ファイルで、`[PASS]` 214 件、`[FAIL]` 0 件。
- 100 回の繰り返し実行で、失敗 0 件。ThreadSanitizer で、警告 0 件。
- 実データで、逐次と並列(2・4・8 スレッド)を、ビット単位で比べて、学習用・検証用、各 3 回の 18 通りが、すべて一致した(偽のデータでは確かめられない、OpenCV のデコードと、前処理の安全性の確認)。

## 9. 計測結果(実データ、バッチサイズ 16、1エポック、Release)

| `num_workers` | 1バッチの生産(平均) | 学習の待ち(合計) | 実行全体 | 高速化 |
|---|---|---|---|---|
| 1 | 551 ms | 6,848 ms | 13.7 s | 1.0 倍 |
| 2 | 270 ms | 2,409 ms | 6.7 s | 2.05 倍 |
| 4 | 165 ms | 762 ms | 5.8 s | 2.37 倍 |
| 8 | 172 ms | 556 ms | 6.0 s | 2.28 倍 |

- 4スレッドで、1バッチの生産時間(165 ms)が、GPU の計算時間(推定 約 165 ms)と、釣り合った。
- 8スレッドでは、速くならなかった。1サンプルの JPEG のデコードが、17 ms から 41 ms に遅くなっており、スレッド同士が、何かを取り合っている。CPU は、8 コア / 16 スレッド(SMT)。読み込みだけを、単独で測ると、2・4・8 スレッドで、1.9 倍・3.3 倍・3.5 倍と、頭打ち。OpenCV の内部スレッドを絞っても、変わらなかった。原因(メモリ帯域、SMT、9p のファイル読み込みなど)は、まだ特定できていない(未確認)。
- `batch_size=1` では、`num_workers` を上げても、効果がない(案Aの制約)。

### 限界

- 各条件、1回ずつの実行で、バッチ数も 17 と少ない。粗い値である。
- この環境(16 スレッド、`/workspaces` は 9p)の値で、他の環境では、適切な `num_workers` が変わる。
