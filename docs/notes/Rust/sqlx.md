## sqlxのモジュールの説明

### sqlx::SqlitePool

SQLite用のコネクションプールの型。`sqlx::Pool<Sqlite>`の型のエイリアス。

#### 使い方

コネクションを開く、閉じるはプールが自動で管理する。プログラマーは「プールを作る」「(必要なら)プールを閉じる」を決める。

1. コネクションを開くタイミング

|タイミング|内容|
|---|---|
|プール作成時(インスタンス生成時)|connect_with は接続確認のために、最初に1本だけコネクションを開く|
|クエリ実行時|空きコネクションがなく、上限(デフォルト10本)に達していない時、その場で新しく開く|

2. 返却、終了のタイミング

|タイミング|内容|
|---|---|
|クエリ終了時|借りたコネクションはプールに返却される(閉じられるわけではない)|
|一定時間使われなかった時|アイドルタイムアウト(デフォルト10分)を過ぎると、プールが自動で閉じる|
|一定時間使い続けた時|最大寿命(デフォルト30分)をすぎると、プールが自動で閉じる|
|プール自体が破棄された時|すべてのハンドル(cloneした物を含む)がdropされると、すべてのコネクションが閉じられる|

#### 性質

- 非同期で並行に使える
  - Webサーバーのように複数のリクエストが同時に来ても、それぞれが別のコネクションを借りてクエリを実行できる。全部使用中なら、空きができるまで`.await`でまつ。
  - `clone`が安い:内部が`Arc`でラップされているため、`clone()`してもコネクションは複製されず、同じプールを指すハンドルが一つ増えるだけ。リポジトリごとに`pool`をフィールドとしてもたせても問題ないのはこれのおかげ


#### コネクションプールとは?

DBを使う際にまず、コネクションを開く必要がある。SQLiteならファイルを開いて設定を読み込む処理、PostageSQLならTCP接続と認証といった感じ。この処理重いから、クエリのたびに「開く→使う→閉じる」を繰り返すのは非効率。そこで、コネクションをあらかじめ開いておいて、使い回すのがコネクションプール。(オブジェクトプールというデザインパターンの一種)

```graph
          ┌──────── SqlitePool ────────┐
リクエストA ─借りる→ │ [conn1] [conn2] [conn3] ... │
リクエストB ─借りる→ │   ↑使用中  ↑使用中  ↑空き   │
          └─────────────────────────────┘
              使い終わったら自動で返却
```
