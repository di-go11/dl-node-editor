# Jenkins CI基盤構築(就活アピール用まとめ)

## 概要(一言でいうと)

研究室サーバー上に**Jenkinsによる自己ホスト型CI基盤をゼロから構築**し、C++/libtorchで書かれた深層学習研究コードに対して、pushのたびに自動ビルド・自動テストが走る仕組みを作った。

## 技術的なポイント(スキルとして語れる部分)

### 1. インフラ構成の設計判断

- **controller/agent分離構成**をDocker Composeで構築(関心の分離、GPUノードとの将来的な切り離しを見据えた設計)
- `docker.sock`を共有しない、UIを学内ネットワークに限定するなど、**セキュリティを意識したセルフホストCIの設計**
- SCMポーリング方式を採用(Webhookが使えない学内ネットワーク特有の制約に対する現実的な妥協案を、比較検討した上で選択)

### 2. Infrastructure as Code(構成のコード化)

- **JCasC(Jenkins Configuration as Code)**を使い、管理者アカウント・権限・agentノード定義をすべてYAMLで管理し、GUIでの手動設定を排除 → 再現可能な環境構築を実現
- 既存の開発用Dockerfileを**マルチステージビルド化**し、開発環境とCI環境の差異を最小限にする設計(「動く環境」を1つのDockerfileで共通化)

### 3. トラブルシューティング力(ここが一番語れる部分)

実際に遭遇し、ログを読んで根本原因を特定・解決した問題の例:

| 症状 | 根本原因 | 特定に使った手法 |
|---|---|---|
| CasCの設定ファイルが「存在しない」エラー | Dockerのvolumeマウントが、ビルド時にCOPYした設定ファイルを実行時に隠していた | ビルド時とランタイムのファイルシステムの違いの理解 |
| 認証設定が効かず誰でもアクセス可能 | YAMLのインデントミスで設定ブロックが別要素の子になっていた | 設定ファイルの構造的検証 |
| `docker-compose exec cat`が「ディレクトリです」エラー | volumeのマウント元パスのtypo(`casc/yaml`)によりDockerが自動でディレクトリを作成していた | 地道な切り分けと一次情報(`docker volume ls`等)の確認 |
| agent接続時に原因不明のプロトコルエラー | 必要なプラグイン(`instance-identity`)が、独自のセットアップウィザード無効化により自動導入されていなかった | HTTPヘッダーの直接検証(`curl`)による外部からの観測 |

→ **「動かない」に対して、推測でなく一つずつ仮説を立てて検証し、ログとHTTPレスポンスなど一次情報から原因を切り分けていくデバッグプロセス**を実践できた、という点は具体的なエピソードとして話しやすい。

### 4. テスト設計の考え方

- 既存のC++テスト資産(11個の実行ファイル)を`ctest`に統合
- **CPU依存/GPU依存でテストにラベルを付けて分離**し、CI環境の制約(GPU非搭載)に合わせて実行範囲を制御する設計

## 使用技術(キーワードとして)

`Docker` / `Docker Compose` / `Jenkins` / `Jenkins Configuration as Code (JCasC)` / `CI/CD` / `CMake` / `CTest` / `C++` / `libtorch` / `YAML` / `Linux` / `セルフホスト型インフラ設計` / `トラブルシューティング`

## 面接で聞かれた時の答え方(STAR形式の一例)

- **状況(S)**: 研究室での深層学習研究において、C++実装の回帰を早期検知する仕組みが無かった
- **課題(T)**: 学内ネットワークの制約(Webhook不可)や、セキュリティ(docker.sock非共有)を踏まえた自己ホストCI環境が必要だった
- **行動(A)**: Jenkins controller/agent構成をDocker Composeで構築し、JCasCで再現可能に設定。構築中に発生した複数の環境固有の不具合を、ログとHTTPレスポンスの一次情報から一つずつ切り分けて解決した
- **結果(R)**: pushをトリガーに自動ビルド・自動テストが走る基盤を整備し、今後の開発効率と品質担保の土台を作った
