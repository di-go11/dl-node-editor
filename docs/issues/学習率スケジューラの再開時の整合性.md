# fix:学習率スケジューラの再開(resume)時の整合性

## 問題点

学習を途中から再開すると、学習率スケジューラが最初からやり直しになり、学習率が初期値 lr0 に戻る。

例: poly(power 0.9)、100 epoch の学習を 60 epoch 目の後に中断して再開した場合

| | 61 epoch 目の学習率 |
|---|---|
| 中断しなかった場合 | lr0 × (1 − 60/100)^0.9 ≒ 0.44 × lr0 |
| いまの実装で再開した場合 | lr0 × (1 − 0/100)^0.9 = **lr0**(初期値に戻る) |

学習の後半でいきなり学習率が大きく戻ると、それまで収束していた重みが大きく動き、val loss が跳ね上がる。中断しなかった場合と同じ学習にならないので、学習結果を比べられなくなる。

### 原因(コードで確認したもの)

| # | 原因 | 該当箇所 |
|---|---|---|
| 1 | OneBatch 型のスケジューラは `step()` を呼ぶたびに内部のカウンタを進める作りで、その状態を checkpoint に保存していない。再開時に新しく作られるので、カウンタが 0 から始まる | `TorchModelTrainer::trainOneEpoch()` の `_lrscheduler->step()`、`adapters/impl/scheduler/PolyLR.hpp`(当時は `infrastructure/torchFunc/Optimizer/Scheduler/OneBatch/PolyLearningRateScheduler.hpp`) |
| 2 | optimizer の `readFrom()` は `loadStateKeepingOptions` で lr を checkpoint から読まず、コンストラクタで指定した値(lr0)のまま残す | `AdamOptimizer` / `AdamWOptimizer` / `SGDOptimizer` の `readFrom()` |
| 3 | 再開位置(`resume.startEpoch`)は `TrainModelUsecase` までしか届いておらず、`IModelTrainer::trainOneEpoch()` もスケジューラも、いま何エポック目かを知らない | `TrainModelUsecase::execute()`、`IModelTrainer.hpp` |

2 は「再開時にハイパーパラメータを変えられるようにする」ための意図した動作なので、これ自体は直さない。スケジューラ側が正しい学習率を設定し直せば問題にならない。

### 経緯

[学習の安定化(シャッフル・データ拡張・学習率スケジューラ).md](学習の安定化(シャッフル・データ拡張・学習率スケジューラ).md) の段階 3 では、学習率は次のように決めていた。そのため、もともとこの問題は起きない設計だった。

- エポック単位で更新する
- 「エポック番号から計算する純粋関数」にする
- checkpoint に保存するものを増やさない

その後、poly を DeepLab と同じくバッチ単位で更新するため OneBatch / OneEpoch の 2 種類を作り、`step()` で状態を進める形にした(feat/LearningRateScheduler ブランチ)。このとき再開時の扱いが抜けていた。

## 方針

**「何ステップ目か」をスケジューラの内部状態から求めず、学習の位置から計算する**(案 A)。段階 3 の「checkpoint に何も足さない」方針を、バッチ単位の更新にも広げる。

### 案 A: 位置から計算する(推奨)

checkpoint はエポックの終わりにしか保存されないので、再開は必ずエポックの切れ目から始まる。そのため、現在のステップ番号は次の式で一意に決まる。

```
step = startEpoch × batchesPerEpoch + (そのエポック内のバッチ番号)
lr(step) = lr0 × (1 − step / totalSteps)^power     ← poly の場合
totalSteps = totalEpochs × batchesPerEpoch
```

- スケジューラは「step を受け取って学習率を返す」副作用のない計算にする(例: `double learningRateAt(uint64_t step) const`)
- 学習率を optimizer に反映するのは呼び出し側(`TorchModelTrainer`)。`_optimizer->updateLearningRate(_lrScheduler->learningRateAt(step))`
- `trainOneEpoch()` に何エポック目かを渡す(`IModelTrainer::trainOneEpoch(IDatasetRepository&, unsigned int epoch)` にする、またはスケジューラ用の開始ステップを別に渡す)
- OneEpoch 型は `step = epoch` として同じ形で扱える(`batchesPerEpoch = 1` と見なす)
- `batchesPerEpoch` は「train の件数 ÷ batch size を切り上げた値」。`IDatasetRepository` は件数を返さないので、取り出す方法を足す(既存の値で求まるならそれを使う)

利点:

- checkpoint の形式を変えなくてよい(この変更より前の checkpoint からも正しく再開できる)
- スケジューラが状態を持たないので、単体テストが書きやすい(step を与えて値を確かめるだけ)
- スケジューラが optimizer への参照を持たないので、寿命の管理がいらない

### 案 B: スケジューラの状態を checkpoint に保存する(不採用案)

`step` のカウンタを checkpoint のメタ情報に書き、再開時に復元する。

- 中断した位置から確実に続けられるが、checkpoint の形式が変わる。`ICheckpointWriter` / `ICheckpointReader` の対象を増やし、古い checkpoint(カウンタなし)をどう扱うかも決める必要がある
- 案 A で同じ結果が得られるので、採用しない

## 実装

| 層 | 変更 |
|---|---|
| adapters/interfaces | スケジューラのインターフェースを `learningRateAt(step)` 形式にする(`step()` で状態を進める形はやめる)。種類(OneBatch / OneEpoch)は今のまま返す |
| adapters/impl/scheduler | `PolyLR` / `CosineLR` / `StepLR` は lr0・totalSteps・power をコンストラクタで受け取り、`learningRateAt(step)` を実装する。`1 − step / totalSteps` が負にならないよう 0 で止める |
| application | `IModelTrainer::trainOneEpoch()` に epoch を渡す。`TrainModelUsecase` は `resume.startEpoch` から回しているループの `epoch` をそのまま渡す |
| adapters/impl | `TorchModelTrainer` が epoch とバッチ番号から step を計算し、バッチの前(OneBatch)またはエポックの最初(OneEpoch)に `updateLearningRate()` を呼ぶ |

- 学習率はバッチを処理する**前**に設定する(step 0 の学習率 = lr0 で 1 バッチ目を学習する)。いまの実装は `trainStep()` の後に `step()` を呼んでいる。どちらに揃えるかで 1 ステップずれるので、テストで固定する

## テスト(`tests/`、CPU のみ)

- `learningRateAt`: step = 0 で lr0、step = totalSteps − 1 で 0 に近い値、step ≥ totalSteps で 0(負や NaN にならない)
- 再開の整合性: 偽物の optimizer で設定された学習率を記録し、次の 2 通りの記録が一致すること
    - 0 epoch 目から最後まで回す
    - k epoch 目まで回したあとに作り直し、startEpoch = k から回す
- OneEpoch 型でも同じことが成り立つ
- 再開後の 1 バッチ目の学習率が lr0 に戻っていない(この issue の回帰テスト)

## 決めること(実装前)

- 再開時に batch size やデータセットを変えた場合(`batchesPerEpoch` が変わる場合)の扱い
    - 新しい `batchesPerEpoch` でそのまま計算する(「エポックの進み具合」としては一致するので、学習率もほぼ連続する)
    - または、変わったことを検出して警告を出す
- 学習率をバッチの前に設定するか後に設定するか(上の「実装」を参照)
