# fix:学習開始前に、モデルの出力チャンネル数とデータセットのクラス数が合っているか確認する

## 問題点

2026-11-20、Pascal VOC 2012(21 クラス)で ResNet-101 を学習させようとしたところ、学習が始まらずに失敗した。

| job | モデル | 結果 |
|---|---|---|
| job-1 | `resnet101-PacalVoc-CrossEntropy-ImageRandmer` | `GET was unable to find an engine to execute this computation`(開始から約 1 秒) |
| job-2〜4 | 同上 / `resnet101-pascalvoc-randmer2` | `CUDA error: device-side assert triggered`(開始から約 30 ミリ秒) |

### 原因(DB のモデル定義で確認したもの)

最後の層 `head_conv` の `out_channels` が **3**(Bloccolli のクラス数)のままだった。11/18 に VOC で学習できた `resnet101-test` と違うのはこの 1 か所だけ。

```
head_conv: in_channels=2048, out_channels=3    ← 失敗したモデル
head_conv: in_channels=2048, out_channels=21   ← 成功したモデル(resnet101-test)
```

- VOC のマスクには 0〜20 のクラス番号が入っているので、CrossEntropy は GPU 上で「ラベル < クラス数(3)」のチェックに引っかかり、device-side assert で止まる
- データの側は問題なかった(train(拡張あり)/ val を factory 経由で 1 エポック読み、マスクの値が 0〜20 と 255 だけであることを確認した)

### なぜ事前に止まらないか

- 出力チャンネル数とクラス数を比べる関数 `validateGraphShapes()`(`entities/domain-objects/ModelGraph/DAG/GraphShapeInference.hpp`)は**すでにあり、テストもある**(`tests/graph_shape_inference_test.cpp`)が、**学習の経路のどこからも呼ばれていない**
    - 確認する内容: 最終出力が特徴マップであること、チャンネル数 = クラス数、H / W = 入力の H / W
- 学習中は、ラベルの範囲を GPU 上でしか確認していない(評価器 `TorchModelEvaluator` は CPU で確認して分かりやすい例外を出すが、train 側にはない)
- そのため、ずれていても学習スレッドが起動し、CUDA が落ちるまで気づけない。エラー文からも原因が分からない

### 二次被害: 1 回 assert が出ると、ai-engine のプロセスが使えなくなる

- device-side assert が起きると、そのプロセスの CUDA コンテキストは壊れたままになり、以降の CUDA 呼び出しがすべて同じエラーになる
- job-2〜4 が開始から約 30 ミリ秒(データを読む前)で落ちているのはこのため。モデルを直しても、**ai-engine を再起動するまで学習できない**
    - 対処: `docker compose -f .deploy/compose.prod.yml restart ai-engine`

## 方針

### 1. 学習開始前に `validateGraphShapes()` を呼ぶ(このissueの本体)

> **2026-11-26 追記**: 形の検証は C++ の新しい RPC `ValidateModelGraph` として、整合性チェックと学習開始の前に Rust から呼ぶことになった。ここの確認(学習開始時)も同じ関数で行う。[学習設定の検証をRustに集める.md](学習設定の検証をRustに集める.md) の段階 2・4 を参照。

対象: `TrainingJob.cpp`

- `checkTrainingJobPreconditions()`(gRPC で学習スレッドを起動する前に呼ばれる)で確認する
    - クラス数は `loadDatasetLabelMap(imageSpec->annotation, command.datasetPath).entryCount()`(`runTrainingJob` と同じ求め方)
    - 入力の形状は `{3, inputHeight, inputWidth}`(`ImageSpec` から)
    - 問題があれば `TrainingPreconditionError` を投げる。StartTraining の応答で返るので、学習スレッドは起動せず、CUDA にも触れない
    - エラー文には、合わないノードと値を入れる(例: 「モデルの出力は 3 チャンネルですが、データセットは 21 クラスです(head_conv の out_channels を 21 にしてください)」)
- `runTrainingJob()` でも同じ確認をする(CLI からの呼び出しは `checkTrainingJobPreconditions` を通らないため。今ある `requireModelId` などと同じ扱い)
- 再開(resume)のとき: モデル構造は checkpoint から復元するので、復元した `graph` に対して確認する(`command.modelGraph` ではなく)
- いまは `resume = false` なら `checkTrainingJobPreconditions` はすぐ return しているので、確認はその前に入れる

### 2. train 側でもラベルの範囲を CPU で確認する(任意)

- `TorchModelEvaluator` と同じように、損失を計算する前に「ターゲットが [0, numClasses) か ignore_index」を確認すれば、1. で防げない原因(ラベルマップとマスクの不一致など)でも分かりやすいエラーになる
- 毎バッチ `min()` / `max()` を取るので少し遅くなる。最初の 1 バッチだけ確認する、などでもよい

### 3. CUDA が壊れたときの扱い(別issueにしてもよい)

- device-side assert のような、プロセスが使えなくなるエラーが出たら、ai-engine のプロセスを終了させる(compose の `restart: unless-stopped` で再起動される)
- あるいは学習ジョブを子プロセスで実行する(変更が大きい)
- 1. と 2. を入れれば、設定ミスで assert が出ることはほぼなくなるので、優先度は低い

## テスト(`tests/`、CPU のみ)

- 出力チャンネル数 ≠ クラス数のグラフで `checkTrainingJobPreconditions()` が `TrainingPreconditionError` を投げる(エラー文にノード ID と両方の数が入っている)
- 出力チャンネル数 = クラス数なら投げない
- 出力の H / W が入力と違うグラフでも投げる
- `resume = false` でも確認される
- (2. を入れるなら)範囲外のラベルを含むバッチで、train が分かりやすい例外を出す

## 確認

- 実サーバーで、`out_channels = 3` のモデルを VOC で学習させ、学習開始の時点でエラーになり、画面に原因が出ること
    - Rust 側が `INVALID_ARGUMENT` をどう返すか(HTTP のステータスとエラー文が画面に出るか)も確かめる
- そのあと、続けて正しいモデルで学習でき、ai-engine の再起動が要らないこと
