# feat:学習の安定化(シャッフル・データ拡張・学習率スケジューラ)

## 問題点

ResNet-101(事前学習なし)を Pascal VOC 2012(train 1,464 枚 / val 1,449 枚、256×256、batch 16、Adam 1e-3、100 epoch)で学習させたところ、損失が安定せず、精度も出なかった。

| 時期 | 様子 | 意味 |
|---|---|---|
| 〜40 epoch | train / val とも 1.1 前後で横ばい | ほぼ全画素を背景と予測し、学習が進んでいない |
| 25〜70 epoch | val だけ 4〜6.6 に何度も跳ねる | 重みが大きく揺れ、BatchNorm の running_mean / running_var が追いつかない |
| 55 epoch〜 | train は 0.1 まで下がるが、val は 2.2 まで上がる | 学習画像を丸暗記している(過学習) |

最終指標: pixel_acc 0.72(全部を背景と答えたときとほぼ同じ)、mIoU 0.06、背景以外のクラスの IoU はほとんどが 0.1 未満。

### 原因(コードで確認したもの)

| # | 原因 | 該当箇所 |
|---|---|---|
| 1 | エポックごとに順番を混ぜていない。毎エポック、train.txt の順に同じバッチを作る | `SegmentationDatasetRepository::reset()` が `_currentIndex = 0` にするだけ |
| 2 | データ拡張がない。画像は縮小して 255 で割るだけで、毎エポック全く同じ入力を見る | `SegmentationDatasetRepository::getNextBatch()` → `ImageNormalizer::normalize()` |
| 3 | 学習率が一定。Adam 1e-3 のまま下がらない | `TrainModelUsecase::execute()` のエポックループに学習率を変える処理がない |
| 4 | ImageNet の事前学習済み重みを使っていない(1,464 枚に対して約 4,200 万パラメータ) | 重みを読み込む仕組みがない(**このissueの対象外**。下の「対象外」を参照) |

評価のときの `setEval()`(BatchNorm を評価モードにする)は正しく入っている(`TorchModelEvaluator.cpp`)ので、そこは原因ではない。

### いまの設定だけでできる対処(このissueの実装を待たずに使える)

- 学習率を 1e-4 に下げる、Adam の weight_decay を 1e-4 にする
- epoch を 40〜50 にする(best は mIoU が上がったエポックで保存されるので、伸ばしすぎても best は残る)
- 事前学習なしなら、ResNet-101 より小さいモデル(ResNet-34 / SegNet)を使う

## 方針

効果が大きく、変更が小さい順に 3 段階で入れる。段階ごとに PR を分け、それぞれ VOC で効果を確かめてから次へ進む。

| 段階 | 内容 | 変更範囲 |
|---|---|---|
| 1 | train のエポックごとのシャッフル | C++ のみ(設定項目は増やさない) |
| 2 | train のデータ拡張(左右反転・拡大縮小+切り抜き) | C++ のみ(まず固定値で入れる。設定項目にするのは効果を確かめた後) |
| 3 | 学習率スケジューラ(poly / cosine / step、warmup)。3a: C++ の計算部分、3b: 設定を送る、3c: 学習率をグラフで表示する | C++ / proto / Rust / フロント |

分担(これまでと同じ): C++・Rust はユーザーが実装し、Claude が計画とレビューをする。`openapi.yaml` とフロントエンド(React)は Claude が担当する。

共通の決まり:

- **validation には何もしない**。シャッフルも拡張もしない(毎回同じ条件で測らないと、エポック間で比べられない)
- **再現性**: `StartTrainingRequest.seed` が指定されていれば、シャッフル順と拡張の乱数もそこから決める。未指定なら毎回変わってよい
- **再開(resume)**: 学習率は「エポック番号から計算する式」にし、checkpoint に追加で保存するものを増やさない

## 段階 1. エポックごとのシャッフル

対象: `infrastructure/dataset/SegmentationDatasetRepository.{hpp,cpp}`, `infrastructure/dataset/DatasetRepositoryFactory.cpp`, `TrainingJob.cpp`

- `SegmentationDatasetRepository` に、読み出す順番 `std::vector<size_t> _order` を持たせる
    - `getNextBatch()` の並列処理の中で、`i = start + index` をそのまま使わず `_order[start + index]` を `_source->getImage()` / `getMask()` に渡す(`ISegmentationData` 側は変えない)
    - `reset()` で、シャッフルが有効なら `_order` を並べ替える(`std::shuffle` + `std::mt19937_64`)
- シャッフルするかどうかはコンストラクタ引数で受け取る(`bool shuffle` と `uint64_t dataSeed`。段階 2 で拡張の乱数にも使うので `dataSeed` という名前にした)
    - `DatasetRepositoryFactory::createVocLayout()` で、`split == DatasetSplit::Train` のときだけ `shuffle = true` にする
    - seed は `TrainingJob` が `command.seed.value_or(std::random_device{}())` で 1 回だけ決め、`DatasetRepositoryFactory` のコンストラクタに渡す(学習 1 回の間変わらない値なので `create()` の引数にはしない)。決めた値はログに出し、未指定の学習も後から同じ順番で再実行できるようにする
    - `torch::manual_seed` と同じ値を使ってよい(乱数生成器が別なので互いに影響しない)
    - CLI(`ConfigReader`)は seed を読まないので、CLI からの学習は常に `random_device` で決まる
- 再開時の順番
    - 「seed + 何回目の reset か」から順番を決めると、再開した場合に回数が 0 から数え直しになり、中断しなかった場合と順番が変わる
    - 学習結果には影響が小さいので、**段階 1 では再開時の順番の一致は求めない**(必要になったら `IDatasetRepository::reset(unsigned int epoch)` にして、エポック番号から決める)

テスト(`tests/`、CPU のみ):

- shuffle = false なら、従来どおり 0, 1, 2, … の順に読む
- shuffle = true なら、1 エポックで全サンプルをちょうど 1 回ずつ読む(重複・抜けなし、最後の端数バッチも含む)
- 同じ seed なら 2 回作っても同じ順番になり、`reset()` を呼ぶたびに順番が変わる
- validation 用(split = Validation)は factory 経由で作っても順番が変わらない

## 段階 2. データ拡張(train のみ)

**まず固定値で、C++ だけで入れる**(決定済み)。segmentation の train では常に拡張し、パラメータは下の固定値を使う。画面の設定項目にするのは、VOC で効果を確かめた後の段階 2b で行う。

| 項目 | 固定値 |
|---|---|
| 拡張するか | segmentation の train では常にする。validation はしない |
| 左右反転 | する(確率 0.5) |
| 拡大縮小の倍率 | 0.5〜2.0 |

### 処理の流れ

```
VocSegmentationData::getImage(i) / getMask(i)   画像(BGR)とラベルマスク(クラス番号、無視は ignore_index)
  → 画像 / マスクの前処理(既存)      入力サイズ W×H に縮小(letterbox)
  → 【新規】拡張(画像とマスクに同じ幾何変換)
      1. 拡大縮小: 倍率 s ∈ [scaleMin, scaleMax] を一様に選んで拡大縮小
      2. 切り抜き / 余白: W×H より大きければランダムな位置で切り抜き、小さければ余白を足す
      3. 左右反転: 確率 0.5
  → ImageNormalizer::normalize()(既存)
```

`SegmentationDatasetRepository::getNextBatch()` では、`_imagePreProcessor->process()` / `_maskPreProcessor->process()` の後、`ImageNormalizer::normalize()` の前に `_augmenter->apply(...)` を呼ぶ(`_augmenter` が `nullptr` なら呼ばない)。

- 既存の縮小(`ResizePreprocessorFactory` / `OpenCvImageResizer`)の後に入れる。縮小の処理は変えない
- **画像とマスクに同じ乱数で同じ変換をかける**。いまの `IImagePreprocessor::process(const ImageData&)` は 1 枚ずつ独立に処理するので使えない。2 枚を一緒に受け取る新しいインターフェースを作る
- マスクの補間は **nearest**(bilinear にするとクラス番号が混ざる)。画像は bilinear
- 余白: 画像は 0(黒)、マスクは **ignore_index**(余白を背景として学習させない)。ignore_index は `SegmentationSpec` から渡す

### 層の分け方

| 層 | 追加するもの |
|---|---|
| entities | `AugmentationConfig`(`horizontalFlip`, `scaleMin`, `scaleMax`)。既定値を固定値(true / 0.5 / 2.0)にする。段階 2 では `ImageSpec` には持たせない |
| application/interfaces/image | `ISegmentationAugmenter`: `void apply(ImageData &image, ImageData &mask, uint64_t sampleSeed) const` |
| infrastructure/image | `OpenCvSegmentationAugmenter`(`cv::resize` / `cv::flip` / 切り抜き・余白)。`AugmentationConfig` と `ignore_index` はコンストラクタで受け取る |
| infrastructure/dataset | `SegmentationDatasetRepository` が augmenter を任意で持つ(`nullptr` なら拡張しない)。factory は train のときだけ、既定値の `AugmentationConfig{}` で作った augmenter を渡す |

- 固定値は `AugmentationConfig` の既定値の 1 か所だけに書く。段階 2b で設定項目にするときは、factory が `AugmentationConfig{}` の代わりに `ImageSpec` から読んだ値を渡すだけで済むようにしておく
- **乱数**: `getNextBatch()` は並列(`IParallelExecutor`)で 1 サンプルずつ処理するので、乱数生成器をスレッド間で共有しない。サンプルごとに `sampleSeed = hash(基準 seed, reset の回数, サンプル番号)` を作って渡し、augmenter の中で `std::mt19937_64` を作る
    - 基準 seed は段階 1 の `dataSeed` と同じ値を使う(factory がすでに持っている)。式は `SegmentationDatasetRepository::sampleSeed()`(splitmix64 で混ぜる)
    - reset の回数は `SegmentationDatasetRepository::reset()` の中で数える
    - こうすると、スレッド数を変えても同じ seed なら同じ結果になる
- `apply` は const にし、状態を持たせない(並列で呼ばれるため)
- **再開時の注意**: 常に有効にするので、この変更より前に学習したモデルを再開した場合も、再開後のエポックから拡張がかかる(学習の途中で入力の条件が変わる)。比べるときは最初から学習し直す

テスト(`tests/`、CPU のみ):

- 幾何変換の後もマスクの値は {0..numClasses-1, ignore_index} のどれかだけ(nearest で補間されていること)
- 画像とマスクに同じ変換がかかる(例: 左半分だけクラス 1 の画像を反転すると、マスクも右半分がクラス 1 になる)
- 出力サイズは常に W×H。縮小したときの余白はマスク側が ignore_index
- 同じ sampleSeed なら同じ結果
- factory 経由で作ったとき、train には augmenter が渡り、validation(split = Validation)は拡張されない

## 段階 2b. データ拡張を設定項目にする(段階 2 の効果を確かめた後)

段階 2 で VOC の過学習が抑えられたことを確かめてから着手する。変更範囲は C++ / proto / Rust / フロント。

### 設定項目(proto / Rust / フロント)

- entities: `AugmentationConfig` に `enabled` を足し、`ImageSpec` に持たせる。factory は `AugmentationConfig{}` の代わりにこれを使う
- proto: `ImageSpec` に `AugmentationConfig augmentation = 5;` を足す
    - `message AugmentationConfig { bool enabled = 1; bool horizontal_flip = 2; float scale_min = 3; float scale_max = 4; }`
    - 未設定(古いクライアント・保存済みモデルの再開)をどう扱うかは、段階 2b の着手時に決める。段階 2 の固定値の挙動(常に拡張)に合わせるなら「未設定 = 有効・既定値」、段階 2 より前の挙動に合わせるなら「未設定 = 拡張なし」
    - `enabled = true` のときの既定値: horizontal_flip = true, scale_min = 0.5, scale_max = 2.0。`0 < scale_min ≤ scale_max` でなければ `INVALID_ARGUMENT`
- C++: `TrainingProtoMapper` と `ConfigReader`(CLI の設定ファイル)で読む
- Rust: entities の `ImageSpec` に `augmentation: Option<AugmentationConfig>`、DTO、`to_proto`、SQLite への記録と読み戻し(migration を追加。既存の行の NULL は上の「未設定」と同じ扱い)
- `openapi.yaml`(Claude): `ImageSpec.augmentation` を任意項目として追加
- フロント(Claude): 学習設定のデータ仕様に「データ拡張」欄(有効、左右反転、拡大縮小の範囲)。保存ファイルは項目がなければ既定値で読めるようにし、version は上げない(`parseDocumentText` が欠けた項目を既定値で補えることを確かめる)

テスト:

- C++: proto / ConfigReader の読み込み(未設定 → 決めた既定、不正な範囲 → エラー)、`ImageSpec` の値が augmenter に渡ること
- Rust: DTO の往復、未設定の往復、SQLite の読み戻し、migration 前の行(NULL)の読み戻し
- フロント: 欄の表示・入力・送信内容、古い保存ファイルを開けること

## 段階 3. 学習率スケジューラ

3 つに分けて進める。3a は C++ だけで完結しており、実装済み。3b・3c はそれぞれ PR を分ける。

| 段階 | 内容 | 状態 |
|---|---|---|
| 3a | C++ の計算部分(スケジューラー・Factory・Trainer への組み込み) | **実装済み**(feat/LearningRateScheduler、2026-11-23) |
| 3b | 設定を送る: proto / C++ の変換 / Rust / openapi / フロントの入力欄 | 未着手 |
| 3c | 学習率を返してグラフにする: 進捗メッセージ / Rust / SQLite / openapi / フロントのグラフ | 未着手 |

### 方式

**ステップ番号 t から学習率を計算する閉じた式**にする。前の値を使わないので、再開しても t さえ分かれば同じ値になる(checkpoint に何も足さない)。

| 種類 | 式(t = 現在のステップ、T = 総ステップ数、lr0 = 初期学習率) | 用途 |
|---|---|---|
| none | 学習率を変えない(Optimizer の設定値のまま) | 既定 |
| poly | lr0 × (1 − t / T)^power(power 既定 0.9) | DeepLab などセグメンテーションでよく使う |
| cosine | min_lr + (lr0 − min_lr) × (1 + cos(π t / T)) / 2 | |
| step | lr0 × gamma^⌊t / step_size⌋(⌊ ⌋ は整数の割り算で求める) | |
| warmup(各方式に共通・任意) | 最初の W ステップは lr0 × (t + 1) / W。t ≥ W では本来の方式を **W だけ後ろにずらして** `inner(t − W)`(本来の方式の総ステップは T − W)。lr0 は `inner(0)`。W は warmup_epochs から求める(PerBatch なら × 1エポックのバッチ数) | 序盤の揺れを抑える。ずらすので、warmup が終わった時点でちょうど lr0 から下がり始める(2026-11-22 決定) |

更新の単位は、種類とは別の設定項目にする(2026-11-23 決定)。

| 更新の単位 | t | T | 主な用途 |
|---|---|---|---|
| PerBatch(既定) | エポック × 1エポックのバッチ数 + バッチ番号 | 総エポック数 × 1エポックのバッチ数 | poly / cosine |
| PerEpoch | エポック | 総エポック数 | step |

### 3a. C++ の計算部分(実装済み)

| 層 | 追加・変更したもの |
|---|---|
| entities | `LearningRateSchedulerConfig`(`std::variant` の None / Poly / Cosine / Step、`updateInterval`、`warmupEpochs`)、`enum class LearningRateUpdateInterval { PerBatch, PerEpoch }` |
| application/interfaces | `IDatasetRepository::batchCount()`(1エポックのバッチ数)、`IModelTrainer::trainOneEpoch(trainData, epoch)`(epoch を受け取る) |
| adapters/interfaces | `ILearningRateScheduler`(`learningRateAt(uint64_t step) const`、`getUpdateInterval()`)、`IOptimizer::updateLearningRate(double)` |
| adapters/impl/lr_scheduler | `PolyLR` / `CosineLR` / `StepLR`(単位を知らない計算だけのクラス)、`WarmupLR`(Decorator)、`createLRScheduler`(エポック単位の設定をステップ単位に換算する Factory。None なら nullptr、不正な設定は `std::invalid_argument`) |
| adapters/impl | `TorchModelTrainer`: PerEpoch はエポックの最初、PerBatch は各バッチの前に `updateLearningRate(learningRateAt(t))`。スケジューラーが nullptr なら何もしない |
| infrastructure | Adam / AdamW / SGD の `updateLearningRate`(全 param_group の `set_lr`)、各 DatasetRepository の `batchCount()` |
| 合成ルート | `TrainingJob`: Dataset を先に作り、`createLRScheduler(command.lrScheduler.value_or({}), epochSize, trainDataset->batchCount())` |

- 再開時: `TrainModelUsecase` が `resume.startEpoch` から回すループの epoch を Trainer に渡し、t をそこから計算するので、中断しなかった場合と同じ学習率になる([学習率スケジューラの再開時の整合性.md](学習率スケジューラの再開時の整合性.md) の案 A)
- 残っているテスト: スケジューラー単体のテスト(`tests/` に新規ファイル)。手元の確認では、warmup + poly(lr0 = 1、W = 4、T = 14、PerEpoch)で t = 0, 1, 2, 3, 4, 5, 9, 13 → 0.25, 0.5, 0.75, 1.0, 1.0, 0.9, 0.5, 0.1 になった。この値をそのままテストにする
- いまは `TrainingProtoMapper` が `lrScheduler` を埋めないので、gRPC からの学習はすべて none で動く(3b で対応)

### 3b. 設定を送る(proto / C++ の変換 / Rust / フロント)

#### proto(`proto/training.proto`/実装済み)

`OptimizerConfig` と同じく `oneof` で、種類とその種類のパラメータを 1 つの値として送る(種類を表す enum を別に持たない。食い違いが起きないため)。

```proto
message PolySchedulerConfig   { double initial_lr = 1; double power = 2; }
message CosineSchedulerConfig { double initial_lr = 1; double min_lr = 2; }
message StepSchedulerConfig   { double initial_lr = 1; uint32 step_size = 2; double gamma = 3; } // step_size はエポック数
message NoneSchedulerConfig   {}

enum LearningRateUpdateInterval {
    LEARNING_RATE_UPDATE_INTERVAL_UNSPECIFIED = 0; // PER_BATCH として扱う
    LEARNING_RATE_UPDATE_INTERVAL_PER_BATCH = 1;
    LEARNING_RATE_UPDATE_INTERVAL_PER_EPOCH = 2;
}

message LearningRateSchedulerConfig {
    oneof config {
        NoneSchedulerConfig   none   = 1;
        PolySchedulerConfig   poly   = 2;
        CosineSchedulerConfig cosine = 3;
        StepSchedulerConfig   step   = 4;
    }
    LearningRateUpdateInterval update_interval = 5;
    uint32 warmup_epochs = 6; // 0 なら warmup しない
}

// StartTrainingRequest に追加(13 は model_id、14 は resume で使用済み)
LearningRateSchedulerConfig lr_scheduler = 15;
```

- `lr_scheduler` が未設定、または `oneof` が未設定なら none(いまの動作。古いクライアントもそのまま動く)
- `initial_lr` を持たせるかどうかは下の「決めること」による。持たせない場合は各メッセージから消し、C++ の Factory に `OptimizerConfig` の learning_rate を渡す

#### C++(`api/grpc/TrainingProtoMapper.cpp`、CLI の `ConfigReader`/実装済み)

- `toLearningRateScheduler()` を `toOptimizer()` と同じ形(`switch (config_case())`)で書き、`command.lrScheduler` を埋める
- 検証して、違反は `INVALID_ARGUMENT`(既存の `requireGreaterThanZero` と同じ書き方):
    - initial_lr > 0、power > 0、0 ≤ min_lr ≤ initial_lr、step_size ≥ 1、0 < gamma ≤ 1
    - warmup_epochs < epoch、none のときは warmup_epochs = 0
- Factory の `std::invalid_argument` は最後の守り。ここで先に弾くと、学習を始める前に分かりやすいエラーを返せる

#### Rust

| 場所 | 変更 |
|---|---|
| entities `training/config/training_config.rs` | `LearningRateScheduler`(enum: None / Poly / Cosine / Step)、`LearningRateUpdateInterval`、`warmup_epochs` を `TrainingConfig` に追加 |
| entities `training/config/` | 上の C++ と同じ検証。実装済み(`LearningRateScheduler::validate`)。[学習設定の検証をRustに集める.md](学習設定の検証をRustに集める.md) の方針で、ハイパーパラメータの誤りは Rust で検出してフロントに返す。上の C++ の検証を最後の守りとして入れるかは、そのissueの「決めること」1 による |
| adapters `http/dto/training_config.rs` | DTO(任意項目。未指定なら none) |
| adapters `training/to_proto/training.rs` | proto への変換 |
| adapters `migrations/0005_*.sql` | `training_config` に列を追加(`lr_scheduler_type TEXT NOT NULL DEFAULT 'none'`、`lr_initial`、`lr_power`、`lr_min_lr`、`lr_step_size`、`lr_gamma`、`lr_update_interval`、`lr_warmup_epochs`)。既存の行は none になる |

#### openapi / フロント(Claude 担当)

- `openapi.yaml`: 学習開始のリクエストに `lr_scheduler` を任意項目として追加(`optimizer` と同じ書き方)
- フロント:
    - entity に `lr-scheduler.ts`(型・既定値・検証)

- C++: `training_proto_mapper_test` に、未設定 → none、各種類の変換、不正値 → `INVALID_ARGUMENT`

- フロント: 欄の表示・切り替え・送信内容、古い保存ファイルを開けること

### 3c. 学習率をグラフで表示する

学習中の進捗画面に、既存の loss のグラフ(`LossChart.tsx`、recharts)と並べて、**エポックごとの学習率の折れ線グラフ**を出す(2026-11-23 追加)。スケジューラーが期待どおりに動いているかを目で確かめられ、loss の変化と学習率の変化を見比べられる。

#### 何を送るか

- 各エポックの **実際に使った学習率**(最後のバッチで使った値)を送る。式から計算した値ではなく、Optimizer から読んだ値にする
    - none のときも、Optimizer の設定値がそのまま表示される
    - フロントで式を計算し直さないので、C++ と TypeScript に同じ式を 2 つ書かずに済む
- PerBatch のときもエポックに 1 点だけ送る(バッチごとに送ると進捗メッセージと DB の行が数十〜数百倍になるため)。warmup やエポック内の細かい変化は、点と点の間を線でつないだ形で見える

#### 変更する場所

| 場所 | 変更 |
|---|---|
| C++ `IOptimizer` | `virtual double learningRate() const = 0;`(Adam / AdamW / SGD は `param_groups()[0].options().get_lr()`) |
| C++ `EpochMetrics` / `EpochReport` | `learningRate` を追加。`TorchModelTrainer` がエポックの最後に `_optimizer->learningRate()` を入れ、`TrainModelUsecase` が `EpochReport` に写す |
| proto `StreamProgressResponse` | `double learning_rate = 10;`(1〜9 は使用済み) |
| C++ 進捗の送信 | `EpochReport.learningRate` を `learning_rate` に入れる |
| Rust `training/from_proto.rs`、entities `training/process.rs` | 受け取って保持する |
| Rust `migrations/0005_*.sql`(3b と同じファイルでよい)、`sql_recorder.rs` | `training_epochs` に `learning_rate REAL` を追加(NULL 可。この変更より前の学習は NULL) |
| Rust `get_training_progress.rs`、`http/dto/training_process.rs` | 進捗(SSE)と履歴の取得で返す |
| `openapi.yaml`(Claude) | 進捗のスキーマに `learning_rate`(nullable)を追加 |
| フロント(Claude) | `entity/training/progress.ts` の点に `learningRate` を足す。`LearningRateChart.tsx` を `ProgressPage.tsx` の `LossChart` の下に置く |

#### グラフの仕様(フロント)

- 横軸はエポック(`LossChart` とそろえる)、縦軸は学習率
- **縦軸は対数目盛にできるようにする**(step だと 1e-4 → 1e-5 → 1e-6 と桁で変わり、普通の目盛りでは後半が 0 に張り付いて見えるため)。既定は対数
- 値が NULL のエポック(この変更より前の学習)は線を切る。全エポックが NULL ならグラフ自体を出さない
- 受信のたびに描き直すので、線のアニメーションは切る(`LossChart` と同じ)
- 任意: 学習設定の画面で、選んだスケジューラーの学習率の推移を事前にプレビューする。ただしフロントで式を計算することになり、C++ と同じ式を 2 か所に持つことになる。やるなら 3a のテストと同じ値で TypeScript 側もテストする

#### テスト(3c)

- C++: `TorchModelTrainer` で、エポックの最後に Optimizer の学習率が `EpochMetrics.learningRate` に入る(none のときは Optimizer の設定値)
- Rust: `learning_rate` の受け取り・保存・読み戻し、NULL の行
- フロント: `appendLossPoint` と同じく、点の追加・同じエポックの置き換え・NULL の扱い。対数目盛で 0 以下の値が来たときに落ちないこと

## 確認(段階ごと)

ResNet-101(`resnet101.json`)を VOC 2012 で、**段階ごとに 1 つずつ足して**学習させ、前の段階と比べる(seed を固定する)。

| 比較 | 期待すること |
|---|---|
| 段階 1 | val の跳ね上がりの回数・大きさが減る |
| 段階 2 | train と val の差(過学習)が縮む。val loss が上がり始めるエポックが遅くなる |
| 段階 3(poly、lr0 = 1e-3) | 後半の val loss が揺れずに下がり、mIoU が上がる |

- 事前学習なしでは mIoU が大きく上がらない可能性が高い。このissueの目標は「学習が安定し、過学習が抑えられること」で、精度の絶対値ではない
- Bloccolli(Original 形式、3 クラス)でも 1 回学習させ、悪くなっていないことを確かめる
- 各段階で、テストはすべて devcontainer の中で行う(C++ は `cmake --build build -j2`、ファイルを足したら cmake を再実行)

### 結果: 段階 1 + 2(2026-11-20)

同じ ResNet-101 構造、VOC 2012、256×256、batch 16、100 epoch で、11/18 の学習(シャッフルも拡張もなし)と比べた。

| | 段階 1 + 2(job-2-3265467726) | 11/18(job-5-1326553487) |
|---|---|---|
| 設定 | Adam **lr 1e-4、weight_decay 1e-4**、seed 10 | Adam lr 1e-3、weight_decay 0、seed なし |
| 100 epoch 目 train / val | 0.78 / 0.89 | 0.12 / 2.25 |
| val loss の最小 | 0.831(98 epoch) | 1.085(38 epoch) |
| val の跳ね上がり | 最大 1.39(70 epoch)、ほかは 1.1 以下 | 4〜6.6 が何度も |
| mIoU の最大 | **0.163**(98 epoch) | 0.073 |
| pixel_acc | 0.733 → 0.77 | 0.73 前後 |
| 学習時間 | 約 50 分 | 約 54 分 |

- **過学習は抑えられた**: 最後まで train と val がほぼ同じ速さで下がり、val が上がり始めるエポックがなかった
- **「全部背景」の状態から抜けた**: 30 epoch あたりから mIoU が上がり始め、最終的に 11/18 の約 2 倍
- **train loss の下がり方は遅い**: 拡張した画像で計算しているので丸暗記できない(想定どおり)。lr を 1/10 にした影響もある。train loss は 11/18 とは直接比べず、val loss と mIoU で比べる
- **まだ学習しきっていない**: 100 epoch 目でも train は下がり続けている。88 epoch 以降は val が 0.83〜0.90、mIoU が 0.12〜0.16 の間で揺れていて、lr が一定のため最後に合わせ込めていないように見える → 段階 3 で改善を期待する
- 拡張を入れても学習時間は延びなかった

注意:

- **lr と weight_decay も同時に変えたため、改善のうちどれだけが段階 1 + 2 の効果かは分けられない**。分けるなら「lr 1e-4、wd 1e-4、拡張なし」(factory で augmenter に `nullptr`)で 1 回学習させて比べる
- 段階 3 の比較の基準は、この学習(lr 1e-4、wd 1e-4、seed 10)にする。上の表の「段階 3(poly、lr0 = 1e-3)」は、lr0 = 1e-4 でも試す
- この job は DB の `training_epochs` に 11〜100 epoch の 90 行しかなく、1〜10 epoch 目が記録されていなかった。原因は未調査

- ~~段階 2 の拡張を画面の設定項目にするか、segmentation の train では常に有効(固定値)にするか~~
    - **決定: まず固定値で C++ だけで入れる**。効果を確かめた後、段階 2b で設定項目にする
- 段階 2b で、`augmentation` が未設定のとき(古いクライアント・保存済みモデルの再開)を「有効・既定値」と「拡張なし」のどちらにするか
- ~~段階 3 の学習率を進捗画面に出すか(出すなら gRPC の進捗メッセージと学習結果の表示も変える)~~
    - **決定: 出す(2026-11-23)**。エポックごとの実際の学習率を進捗で送り、グラフにする(段階 3c)
- 段階 3b: 初期学習率 lr0 をどちらで持つか
    - スケジューラーの設定に `initial_lr` を持たせる(いまの C++ の実装)。この場合 Optimizer の `learning_rate` は、スケジューラーを使うと最初のバッチで上書きされて使われない。画面では Optimizer の学習率欄を無効にするなどして、2 つの値が食い違わないようにする
    - スケジューラーの設定から外し、Optimizer の `learning_rate` を lr0 にする。値が 1 か所だけになる。C++ の Factory に `OptimizerConfig` の learning_rate を渡す変更が要る
- ~~段階 3b: 再開時に、保存した設定と違う `lr_scheduler` を指定できるようにするか~~
    - **決定: 指定できない(2026-11-23)**。再開時は保存した設定を必ず使う。`ResumeTrainingConfig` に `lr_scheduler` を持たせず、`apply_to` の `..saved` で前回の値が残るようにする
    - 注意: `lr_scheduler` を `OptimizerConfig` の中に入れる場合、再開時に変えてよい `optimizer` と一緒に上書きされてしまう。`apply_to` で optimizer を差し替えるときも、スケジューラーだけは保存した値を残す
- 段階 3b: 再開時に変えてよい項目(`epoch`・`batch`・Optimizer の `learning_rate`)を変えた場合の扱い。どれも総ステップ数 T・1エポックのバッチ数・lr0 が変わるので、スケジューラーの設定を固定しても、再開の前後で学習率がつながらない。許して警告を出すか、スケジューラーを使っているときは変更を禁止するか

## 対象外(別issue)

進め方: 段階 1〜3 を入れたあと、事前学習なし(ゼロから)でも ResNet-34 と Bloccolli で学習が安定することを確かめる。そのあとで、下の「事前学習済み重みの読み込み」を別issueにする。
(このアプリの目的はモデル構造の試行錯誤なので、ゼロから学習させた同じ条件での比較がまず成り立つことを優先する。事前学習は「公開ベンチマークで論文並みの精度を出す」ために後から足す)

- **ImageNet の事前学習済み重みの読み込み**: 精度への効果は一番大きいが、変更も一番大きい
    - 形が変わっていないノードにだけ重みを読み込み、構造を変えた部分やヘッドは乱数から始められるようにする(再開用の重み読み込みの仕組みを、名前の対応表で一部だけ読む方向に広げる)
    - torchvision の重み(`.pth`)を libtorch で読める形に変換し、重みの名前(`layer1.0.conv1.weight` など)とグラフのノード ID を対応させる仕組みが要る
    - 入力の正規化も ImageNet の平均・標準偏差に合わせる必要がある(いまは 255 で割るだけ)
- **出力の粗さ**: いまのヘッドは 1/32 の解像度から ×32 に拡大する(FCN-32s と同じ)。skip 接続(FCN-8s)や dilated conv(DeepLab)はノードの組み方で作れるので、コード変更ではなくモデル定義の問題
- **SBD で増やした VOC(train 10,582 枚)**: データセット側の話
