# refactor:学習ジョブを学習ごとの子プロセスで動かす

## 問題点

いまの ai-engine は 1 つのプロセスの中で、gRPC の受付と学習(`TrainingJobManager` が作る学習スレッド)の両方を行う。学習が終わってもプロセスは動き続けるため、次の問題がある。

| # | 問題 | 原因 |
|---|---|---|
| 1 | 学習が終わっても GPU の専用メモリが解放されない。同じ GPU をほかのプログラムで使えない | libtorch のキャッシュアロケータは、使い終わったメモリを OS(ドライバ)に返さずプロセスの中に取っておく。CUDA の初期化分(数百 MB)はプロセスが終わるまで返らない |
| 2 | 1 つの学習で CUDA が壊れると、ai-engine を再起動するまで次の学習ができない | device-side assert などはプロセスの CUDA コンテキストを壊したままにする(「2026-11-20/学習開始前のモデル出力とクラス数の確認.md」の 3.) |
| 3 | 応答しなくなった学習を止められない | 停止はエポックの区切りで `TrainingStopToken` を見るだけで、学習スレッドを外から終わらせる手段がない |

1 のうちキャッシュの分だけなら、学習の後に `c10::cuda::CUDACachingAllocator::emptyCache()` を呼べば返せる(数行の変更。このissueとは別に先に入れてよい)。CUDA の初期化分と、2・3 はプロセスを分けないと解決しない。

## 方針

**学習のたびに子プロセスを起動し、学習が終わったら子プロセスごと終わらせる。** プロセスが終わると、GPU のメモリは CUDA の初期化分も含めて OS がすべて回収する。

```
[ai-engine(親)] gRPC の受付・ジョブの管理・進捗の配信。CUDA は使わない
   └─ 学習のたびに起動 → [学習プロセス(子)] libtorch・CUDA で学習(runTrainingJob)
                            ├─ 進捗を親に送る(パイプ)
                            └─ 学習が終わったら終了する
```

- `TrainingJobManager` は学習の実行を `JobRunner`(関数)として受け取る作りなので、**子プロセスを起動する `JobRunner` に差し替えるだけ**にし、ジョブの管理・進捗の置き場所(`TrainingProgressStore`)・`StreamProgress` は変えない
- 子プロセスは同じバイナリ(`ai_engine_app`)を別の引数で起動する。イメージやデプロイの手順は変わらない
- 同時に動かす学習は、いまと同じく 1 つまで(`TrainingJobBusyError`)

## 設計

### 起動と依頼の受け渡し

- 親は `posix_spawn` で `ai_engine_app --run-job` を起動する
- 依頼(`StartTrainingCommand`)は、子の標準入力に **proto の `StartTrainingRequest` をシリアライズして**渡す。子は親と同じ `toStartTrainingCommand()` で戻す(C++ の型を自前で直列化する処理を書かずに済む)
- 実行環境の設定(`TrainingRuntimeConfig`。checkpoint の保存先など)は環境変数で読んでいるので、子にそのまま引き継ぐ

### 進捗(子 → 親)

- 専用のパイプ(標準出力とは別の fd 3)で、エポックごとに `StreamProgressResponse` を **長さ付きで**送る(4 バイトの長さ + 本体)
    - 標準出力・標準エラーは学習のログ(`std::cout` の numClasses など)なので混ぜない。親と同じところ(コンテナのログ)に出す
- 親の `JobRunner` は受け取った進捗を `TrainingProgressStore` に入れる(いまの `onEpochCompleted` と同じ扱い)
- 終わりの状態(Completed / Stopped / Failed と理由)も最後のメッセージで送る

### 停止(親 → 子)

- `StopTraining` が来たら、親は子に `SIGTERM` を送る。子は受け取ったら `TrainingStopToken` を立て、いまと同じくエポックの区切りで止まる
- 一定時間(例: 1 エポックぶん + 余裕。設定で変えられるようにする)待っても終わらなければ `SIGKILL` で終わらせ、状態は Stopped(理由: 強制終了)にする(問題点 3)

### 異常終了

- 子がシグナルで落ちた・最後のメッセージを送らずに終わったときは Failed にし、理由に終了コード / シグナルを入れる(問題点 2: 壊れるのは子だけで、親は次の学習を受け付けられる)

### 親で CUDA を使わない

親が一度でも CUDA を使うと、親にも初期化分のメモリが残る。いま親で CUDA を使っているのは次の 2 か所。

| 場所 | 対応 |
|---|---|
| `CudaCapabilityProvider`(`torch::cuda::is_available()` / `device_count()`) | 起動時に子プロセス(`ai_engine_app --capabilities`)で 1 回調べて結果を持つ(下の「決めること」2) |
| `checkTrainingJobPreconditions()`(再開の checkpoint のメタ情報とグラフを読む) | CPU で読んでいるので CUDA は初期化されない(確認する)。そのままでよい |

`ValidateModelGraph`(`checkModelGraph`)は torch を使わないので、親のままでよい。

## 段階

1. **子プロセスでの実行と進捗**: `--run-job`、パイプでの進捗、終わりの状態。親の `JobRunner` を差し替える
2. **停止と強制終了**: `SIGTERM` → 猶予 → `SIGKILL`
3. **capabilities**: 親で CUDA を使わないようにする
4. **確認**: 下の完了条件

## テスト

- 子プロセスの `JobRunner`: 偽の子(進捗を数回送って終わるだけのプログラム、途中で落ちるプログラム)で、進捗が store に入る・終わりの状態・異常終了が Failed になる
- 停止: `SIGTERM` で Stopped になる。応答しない子は猶予の後に `SIGKILL` され Stopped(強制終了)になる
- 既存の `training_job_manager_test` はそのまま通る(`JobRunner` を差し替えるだけなので)

## 決めること

1. **進捗の送り方**
    - 案 A(おすすめ): パイプで `StreamProgressResponse` を長さ付きで送る。proto を使い回せ、依存が増えない
    - 案 B: 子も gRPC で親に接続する(Unix ドメインソケット)。拡張しやすいが、子にも gRPC のクライアントが要り、作るものが増える
2. **capabilities の調べ方**
    - 案 A(おすすめ): 親の起動時に子プロセスで 1 回調べて、結果を持つ。GPU の抜き差しはまれなので十分
    - 案 B: 問い合わせのたびに子プロセスで調べる。毎回数秒かかる
    - 案 C: NVML(`nvidia-smi` の元のライブラリ)で調べる。libtorch とは別の依存が増える
3. **学習の開始が数秒遅くなることを許すか**: 子プロセスが毎回 libtorch を読み込み、CUDA を初期化するため。学習全体の時間に比べれば小さい

## 対象外

- 複数の学習を同時に動かすこと(いまと同じく 1 つまで)
- CLI(`ai_engine_app` を引数なしで動かす学習)。いまと同じく 1 プロセスで学習し、終わればプロセスが終わるので問題にならない

## 完了条件

- 学習が終わった後、`nvidia-smi` で ai-engine が GPU のメモリを持っていない(親は CUDA を使わない)
- 1 つの学習で device-side assert が起きても、ai-engine を再起動せずに次の学習を始められる
- `StopTraining` でエポックの区切りに止まる。止まらない学習も、猶予の後に強制終了できる
- 学習中の画面の進捗・学習率のグラフ、DB への記録が、これまでどおり動く
